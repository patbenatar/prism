# Prism — independent code review

Reviewer: lead-assigned independent reviewer. Date: 2026-09-19.
Scope: the whole application against `PLAN.md`, `AGENTS.md`, `DESIGN.md` and
`docs/research/*.md`. Application code was read, not modified. Every finding
below was confirmed with a throwaway probe (`bin/rails runner`, a temporary
integration test) unless it is explicitly marked as reasoned-but-unproven; the
probes were deleted afterwards.

Suites run once, against `TEST_DATABASE=prism_test_review`:

| Suite | Result |
| --- | --- |
| `bin/rails test` | 384 runs, 1676 assertions, 0 failures, 0 errors |
| `bin/rails test:system` | 28 runs, 167 assertions, 0 failures, 2 errors |

The two system errors are both in `test/system/features/pending_review_test.rb`,
which belongs to the in-progress `ws-f-e2e` workstream and is out of scope for
this review. All 18 system tests under `test/system/*.rb` pass.

---

## Summary verdict

**Ship-quality with four things to fix first.** The parts that are hardest to get
right are right. `Markdown::Sanitizer` is a genuinely strong boundary — I threw
sixteen payloads at it (`javascript:` in several encodings, `data:` URLs,
`onerror`, `style`, SVG animation, `formaction`, mXSS via `<math>`/`<noscript>`)
and every one was neutralised. `Diff::Patch`, `Review::AnchorResolver` and
`Review::Anchor` encode the LEFT/RIGHT and contiguity rules from the research
document faithfully, including the invariant that a LEFT anchor carries a base
line and `right_of_left` is display-only. Cache keys are namespaced by user id
everywhere. `owner`/`repo`/`path` are URL-escaped before they reach an API path,
so there is no SSRF through the route parameters.

What needs fixing: one view renders GitHub-sourced HTML with `raw` and no
sanitizer; the sanitizer's safelist keeps arbitrary `id` attributes from
repository HTML, which the app then relies on for Turbo Stream targeting; the
child-block weaving in the file-view helper emits duplicate DOM ids for a
specific list shape; and the write controllers turn ordinary GitHub errors and
malformed form input into 500s. There is also no Content-Security-Policy, and a
shared test fixture is internally inconsistent in a way that makes the
"contract" tests pin the wrong answer.

## Findings

### High

#### H1 — GitHub comment HTML is rendered with `raw` and is never sanitized

`app/views/shared/_comment_card.html.erb:46-48`

```erb
<%# body_html comes from GitHub's GraphQL bodyHTML and is sanitized by
    Markdown::Sanitizer before it reaches a view. %>
<%= comment.body_html.present? ? raw(comment.body_html) : simple_format(comment.body) %>
```

The comment is false. `Github::Client#build_comment` (`app/services/github/client.rb:533`)
assigns `data[:bodyHTML]` verbatim, and nothing between the transport and the
view calls `Markdown::Sanitizer` or `ApplicationHelper#github_html`. A `grep` for
`Sanitizer` finds exactly two call sites: `Markdown::Renderer#build_block` and
`ApplicationHelper#github_html`, and this view uses neither.

Confirmed by rendering the partial with a hand-built `ReviewComment`:

```
<div class="comment-body md-prose md-prose-compact">
  <p>hi</p><img src=x onerror="alert(document.domain)"><a href="javascript:alert(1)">click</a><div id="pending_tray">hijack</div>
```

This is the only `raw` of remote HTML in the codebase, and it is on the one
surface whose content is written by other people. It is not exploitable against
GitHub as it behaves today, because GitHub sanitizes `bodyHTML` server-side — so
the practical severity rests entirely on an undocumented guarantee from a third
party, which is exactly the dependency `AGENTS.md` says not to take ("Rendered
Markdown and GitHub `bodyHTML` pass through `Markdown::Sanitizer` before
`raw`/`html_safe`"). Note that the sibling branch on the same line already does
the right thing: `simple_format` sanitizes by default.

**Fix.** Replace `raw(comment.body_html)` with `github_html(comment.body_html)`
and delete the comment that claims it already happens. One word, no behaviour
change on well-formed input, and it makes the assertion in the comment true.

#### H2 — The sanitizer keeps arbitrary `id` attributes from repository HTML, and the app targets by id

`app/services/markdown/sanitizer.rb:25-32` includes `id` in the safelist. With
`unsafe: true` in the renderer, a raw HTML block in a reviewed `.md` file reaches
that safelist intact. Confirmed:

```
Markdown::Document.parse('<div id="pending_tray">hijacked</div>')
→ html_block 1-1: <div id="pending_tray">hijacked</div>
```

Every Turbo Stream target and every `document.getElementById` in the app is a
fixed or derivable id: `pending_tray`, `file_threads`, `outdated_threads`,
`threads_<block_id>`, `composer_<block_id>`, `thread_<node_id>`,
`comment_<node_id>`. `getElementById` returns the first match in document order,
and the tray is rendered through `content_for :tray`, which the layout yields
*after* `</main>` (`app/views/layouts/application.html.erb:58`) — so a decoy
placed anywhere in the rendered document wins.

Scenario: the author of a pull request adds `<div id="pending_tray"></div>` to a
Markdown file. A reviewer opens that file and posts a comment. The
`turbo_stream.replace("pending_tray", …)` from
`ReviewCommentsController#pending_tray_stream` lands on the decoy instead of the
real tray, so the pending count and the Submit/Discard controls silently stop
updating for the rest of the session. The same trick against `composer_<id>`
makes `composer_controller.js:46` open the composer into the attacker's element
rather than under the block.

No script executes — this is disruption and misdirection, not code execution —
but it is repository-controlled content steering the reviewer's own UI.

**Fix.** Do what GitHub does: prefix or drop `id` at the sanitizer boundary. The
renderer already passes `header_ids: "user-content-"` for comrak-generated
anchors, so the only ids that need rewriting are the ones in raw HTML blocks.
Either drop `id` from `ATTRIBUTES` and re-add comrak's heading ids after
sanitizing (same pattern the helper already uses for child markers), or scrub any
surviving `id` to `user-content-<id>` in `Sanitizer.call`.

#### H3 — Two child blocks that start on the same source line produce duplicate DOM ids and an unreachable gutter

`app/helpers/pull_request_files_helper.rb:82`

```ruby
by_line = children.index_by { |child| child.block.start_line }
```

`index_by` keeps the last entry for a duplicate key. A list item whose first
child is itself a list on the same line — `- - a` — yields an outer `<li>` and an
inner `<li>` that both report `start_line == 1`, so both are decorated with the
*inner* child's annotation.

Confirmed on `"- - a\n- b\n"`:

```
ids: ["block_b2-1-1-3ba8ce5a", "block_b2-1-1-3ba8ce5a", "block_b3-2-2-1c90d0d2"]  dup? true
thread container ids: ["threads_b2-1-1-3ba8ce5a", "threads_b2-1-1-3ba8ce5a", ...] dup? true
```

Three consequences: the document contains duplicate `id` values for
`block_*`, `threads_*` and `composer_*`; the outer list item (block `b1`) gets no
gutter button at all and cannot be commented on; and a comment posted from the
inner item's "+" is appended by
`turbo_stream.append("threads_<id>")` into the *outer* container, so it renders
against the wrong bullet. `composer_controller.js` has the mirror problem — the
button lives in the inner `<li>` but `getElementById` finds the outer slot.

The trigger is narrow (`- - x`, `1. - x`, and similar same-line nestings) but it
is valid CommonMark and appears in real documents.

**Fix.** Key by identity rather than by line, and consume each child once:

```ruby
remaining = children.group_by { |child| child.block.start_line }
# …
child = remaining[sourcepos_start_line(element)]&.shift
```

`fragment.css("li[data-sourcepos]")` walks the DOM outermost-first, which matches
the order `self_and_descendants` produces, so shifting off the front assigns the
outer element to the outer block. Add a golden fixture for `- - a`.

#### H4 — The write controllers 500 on ordinary GitHub errors and on malformed anchor parameters

`app/controllers/review_comments_controller.rb:20` rescues
`LineNotCommentable`, `Unprocessable`, `RateLimited` and `GraphQLError`.
It does not rescue `Github::NotFound` or `Github::Forbidden`, and the controller
does not `include GithubErrorHandling`. The same is true of
`ReviewThreadsController` (no `NotFound`) and `ReactionsController` (no
`NotFound`, no `Forbidden`).

Separately, `build_anchor` (`:80-94`) hands raw params straight to
`Review::Anchor`, whose constructor raises `ArgumentError` on a bad side or a
reversed range, and nothing rescues `ArgumentError`.

Confirmed with a temporary integration test (all three raise out of the action):

```
[WRITE 404]        RAISED Github::NotFound: Not Found
[BAD SIDE]         RAISED ArgumentError: side must be one of [:left, :right]
[REVERSED RANGE]   RAISED ArgumentError: start_line must be before line
```

Realistic scenario for the first: the reviewer's access to the repository is
revoked, or the pull request is deleted, while their file view is still open.
They click "Add single comment" and get a 500 error page instead of "Not found
on GitHub, or you don't have access to it." The `ArgumentError` cases need a
stale page or a tampered form, so they are lower-impact, but they are still an
unhandled exception on a public write endpoint.

**Fix.** `include GithubErrorHandling` in the four write controllers (its
`github_not_found` / `github_forbidden` handlers already render the right pages),
and wrap `build_anchor` so an `ArgumentError` becomes the same inline composer
error that a 422 already produces — `render_composer_error` is already written
and takes any object responding to `user_message`.

### Medium

#### M1 — No Content-Security-Policy

`config/initializers/content_security_policy.rb` is the untouched Rails
scaffold: every line is commented out. Confirmed at runtime —
`Rails.application.config.content_security_policy` is `nil`, so no CSP header is
sent and `csp_meta_tag` in the layout emits nothing.

For an app whose entire purpose is rendering other people's HTML, CSP is the
second layer that makes H1 and H2 survivable rather than exploitable. The layout
also loads a stylesheet from `fonts.googleapis.com` and renders `<img>` tags from
arbitrary repositories, both of which a policy should name explicitly.

**Fix.** A starting policy that matches what the app actually uses:

```ruby
policy.default_src :self
policy.script_src  :self
policy.style_src   :self, "https://fonts.googleapis.com"
policy.font_src    :self, "https://fonts.gstatic.com"
policy.img_src     :self, :data, :https      # repo images come from anywhere
policy.object_src  :none
policy.frame_src   :none
policy.base_uri    :self
policy.form_action :self
```

Importmap and Stimulus need no `unsafe-inline` for scripts. Ship it in
report-only first if you want to see what breaks.

#### M2 — A merged pull request never shows as "Merged" on the pull request list

`app/services/github/client.rb:456` reads `merged: data[:merged]`.
`docs/research/github-api.md` §2.2 lists the fields present on
`GET /repos/{owner}/{repo}/pulls` and `merged` is not among them — it is added by
the single-PR endpoint (§2.3). The list response carries `merged_at` instead.

So on `/:owner/:repo/pulls`, `PullRequestsHelper#pull_request_state`
(`app/helpers/pull_requests_helper.rb:12`) sees `merged == nil` for every row and
falls through to `state == "closed"`, rendering a merged pull request as
**Closed**. The overview screen, which uses the detail endpoint, is correct.

This is invisible to the suite because `test/fixtures/github/pulls.json:9,34`
invents a `merged` key the real list endpoint does not send.

**Fix.** `merged: data[:merged].nil? ? data[:merged_at].present? : data[:merged]`,
and delete `merged` from `pulls.json` so the fixture describes GitHub rather than
the code.

#### M3 — The shared `guide.md` fixture contradicts its own patch, so the contract tests pin the wrong anchors

`test/fixtures/github/pull_files.json:12` declares the second hunk as
`@@ -10,3 +12,4 @@ ## Section`, meaning head lines 12–15 are
`Prose here.` / `New line.` / `Another.` / `Tail.`.
`test/fixtures/github/guide.md` actually has `## Section` on line 13 and
`Prose here.` on line 15 — two lines of drift. The *base* side used by
`test/integration/pull_request_files_test.rb:21-33` is consistent with the patch;
it is the head fixture that is wrong.

Confirmed by running the real pipeline over the two fixtures:

```
heading    13-13 added      {line: 13, side: "RIGHT"}      ← the "## Section" heading
paragraph  15-18 unchanged  {line: 15, side: "RIGHT"}      ← the paragraph that actually changed
```

The heading, which the patch never touches, is marked `added`; the paragraph that
gained `New line.` and `Another.` is marked `unchanged` and gets a single-line
anchor onto a *context* line. `github_fixture_contract_test.rb:71`
(`assert_equal [3, 13], changed`) and `pull_request_files_test.rb:74`
(`assert_select "[data-change=added]", 2`) both lock this in.

The knock-on effect is the important one: with a consistent head file, block
12–15 would be entirely in-diff and contiguous, and `AnchorResolver` would emit a
**multi-line** anchor. As the fixtures stand, no block in the shared fixture ever
produces one, so the multi-line path — the feature that distinguishes Prism from
commenting on a single line — is exercised only by pure unit tests and never
through a controller or a browser.

**Fix.** Delete `Yet more filler.` and its blank line from `guide.md` and close
the gap between `## Section` and `Prose here.` so the head file matches what the
patch reconstructs. Then update the two assertions above to the corrected block
lines, and add an assertion that the 12–15 block yields
`start_line: 12, line: 15`.

#### M4 — A revoked token on the Markdown preview endpoint does not sign the user out

`app/controllers/markdown_previews_controller.rb:9`

```ruby
rescue_from Github::Error, with: :render_error
```

`ActiveSupport::Rescuable` searches handlers in reverse registration order, and a
subclass's handlers are appended after the parent's. `Github::Error` is the
superclass of `Github::Unauthorized`, so this handler shadows
`Authentication`'s `rescue_from Github::Unauthorized, with: :handle_revoked_token`.

Scenario: the user revokes Prism's authorization on GitHub, then types in a
composer and clicks Preview. Instead of `revoke_token!` clearing the dead token
and redirecting to sign-in, they get a small red error fragment, and the revoked
token stays in the database to be retried on the next request.

`MentionablesController:9` gets this exactly right — it enumerates the error
classes and deliberately excludes `Unauthorized`, with a comment explaining why.

**Fix.** Enumerate the same way here: `rescue_from Github::Forbidden,
Github::NotFound, Github::RateLimited, Github::GraphQLError, Github::Unavailable,
Github::Unprocessable, with: :render_error`.

#### M5 — Every write fetches the pull request's review list twice

Measured on a review-mode comment create (temporary integration test, request
log):

```
GET  /repos/acme/docs-site/pulls/42
GET  /repos/acme/docs-site/pulls/42/reviews?per_page=100     ← CommentWriter#ensure_pending_review
POST /graphql                                                ← addPullRequestReviewThread
POST /graphql                                                ← reviewThreads refetch
GET  /repos/acme/docs-site/pulls/42/reviews?per_page=100     ← ReviewCommentsController#current_pending_review
```

`Github::Client#reviews` is deliberately uncached (`client.rb:132`), so these are
two real round trips to the same URL inside one request.
`Review::CommentWriter#ensure_pending_review` already knows the review it used
and throws it away. Writes cost 5 points each against GitHub's 900/min/endpoint
budget, and `PLAN.md` treats the rate limit as scarce.

**Fix.** Memoize `Github::Client#pending_review` per client instance (the client
is already per-request via `Authentication#github`), or have `CommentWriter`
expose the review it resolved so `current_pending_review` can reuse it.

#### M6 — A thread with more than 100 comments silently loses the rest

`app/services/github/queries.rb:58` requests `comments(first: 100)` and selects
`pageInfo { hasNextPage endCursor }`, but nothing ever reads it.
`Queries::THREAD_COMMENTS` (`:82`), the follow-up query written for exactly this
case, has no callers — `grep` finds one hit, its own definition.

`Github::Client#review_threads` paginates the thread list correctly but not the
comments inside a thread, so a long-running conversation is truncated with no
indication. Every fixture sets `hasNextPage: false`, so no test can see it.

**Fix.** Either wire `THREAD_COMMENTS` into `build_thread` behind a
`hasNextPage` check, or — if 100 is judged enough for v1 — delete the dead query
and render a "showing the first 100 comments, continue on GitHub" note when
`hasNextPage` is true. Leaving an unused query that looks like the feature works
is the worst of the three.

#### M7 — A posted comment can vanish if GitHub's read-after-write is not immediate

`app/controllers/review_comments_controller.rb:129`

```ruby
thread = fresh_threads.threads.find { |t| t.node_id == thread_node_id }
```

If the refetched `reviewThreads` does not yet contain the thread the mutation
just returned, `thread` is `nil`; `review_comments/_thread` is guarded by
`if thread.present?` and renders nothing, while
`turbo_stream.update("composer_#{block_id}", "")` clears the composer
regardless. The reviewer's text is gone and nothing appears in its place, with no
error.

Re-fetching is the right call (`PLAN.md` principle 1), but the nil case needs a
floor.

**Fix.** Fall back to the thread the mutation returned when the refetch misses
it, and only clear the composer once something has been rendered into the thread
container.

### Low

- **L1 — A file-level comment moves after a reload.** `render_new_thread` appends
  the new thread into `threads_<block_id>`, so a file-level fallback comment
  first appears under the block it quotes. On the next page load
  `BlockMapper#bucket_threads` (`block_mapper.rb:108`) routes `subjectType: FILE`
  to the `file_threads` section at the top of the page, and it jumps. Either
  stream it into `#file_threads` when `subject_type == "file"`, or say in the
  composer that a file-level comment lands at the top.

- **L2 — The composer does not work without JavaScript.** Replies, resolve,
  delete, edit and reactions are all real `form_with` / `button_to` forms and
  degrade correctly. The block composer does not: the gutter "+" is a
  `<button type="button">` whose only behaviour is `data-action="composer#open"`,
  and the form lives inside a `<template>` (`_composer_template.html.erb:10`),
  which is inert without JS. That means Prism's headline action is the one thing
  with no HTML fallback, which is the opposite of the ordering `AGENTS.md`
  implies. Defensible as a v1 decision; worth stating explicitly rather than
  leaving implied.

- **L3 — Production uses `:memory_store`, not Solid Cache.**
  `config/environments/production.rb:48`, with a comment explaining it as a
  single-instance choice. `solid_cache` is in the `Gemfile` and `PLAN.md` names
  it. With more than one Puma worker the per-user cache becomes per-process, and
  `memory_store`'s default 32 MB ceiling will evict the 7-day file-content
  entries that the TTL table is counting on. A deliberate deviation, but
  `PLAN.md` asks for deviations to be noted rather than left to be discovered.

- **L4 — `ReviewsController#create` is unreachable.** No view or Stimulus
  controller posts to `repo_pull_reviews_path`; the composer's "Start a review"
  button goes to `ReviewCommentsController#create` with `commit=review`, and the
  tray only renders once a pending review exists. The action, its route and
  `CommentWriter#ensure_pending_review`'s "public so callers that only need the
  review can reuse it" comment describe an affordance that is not on the page.

- **L5 — A GraphQL `NOT_FOUND` on threads 404s the whole file view.**
  `Review::Page#load_review_state` (`page.rb:181-192`) rescues `RateLimited`,
  `Forbidden` and `Unavailable` and renders the document without comments —
  exactly right. `Github::NotFound` is not in that list, so it propagates to
  `GithubErrorHandling#github_not_found` and the reviewer loses the document too.
  Adding `Github::NotFound` to the same rescue matches the stated intent ("the
  document itself is still what the reviewer came for").

- **L6 — No size ceiling before parsing.** `Github::Client#file_content` fetches
  and `Markdown::Renderer` parses whatever GitHub serves, with no byte limit. The
  `MAX_HTML_REGION_*` caps guard one pathological shape but not overall size. A
  multi-megabyte generated `.md` file in a pull request will parse, sanitize,
  highlight and serialise through Nokogiri on the request thread. A cap around
  1–2 MB, falling back to the existing `missing_content?` empty state, closes it.

## API-call budget per screen

Measured with a `WebMock.after_request` counter on a real request in a temporary
integration test (`config.cache_store = :null_store` in test, so these are
cold-cache numbers — the warm numbers in development depend on the TTL table in
`Github::Client::TTL`).

| Screen | Calls | Breakdown |
| --- | --- | --- |
| `/repos` | 1 | `GET /user/repos` (×N for `?page=N`, capped at 5) |
| `/:owner/:repo/pulls` | 2 | `GET /repos/…`, `GET /repos/…/pulls` |
| PR overview | 4 | `pulls/:n`, `pulls/:n/files`, `pulls/:n/reviews`, `POST /markdown` |
| Rendered file view | 6 | `pulls/:n`, `pulls/:n/files`, `contents/…?ref=head`, `contents/…?ref=base`, `POST /graphql` (reviewThreads), `pulls/:n/reviews` |
| Comment write (review mode) | 5 | `pulls/:n`, `pulls/:n/reviews`, `POST /graphql` ×2, `pulls/:n/reviews` |

No N+1 anywhere: nothing is fetched per row, per file or per block, and the file
view's base-side read is correctly skipped for added files and for diffs with no
deletions (`Review::Page#base_side_needed?`). The pull request overview computes
the Markdown-file count once from the file list it already has rather than per
row, which is the right call and is documented at the call site.

Two avoidable calls:

1. The duplicate `GET /pulls/:n/reviews` on every write (**M5** above) — 5 → 4.
2. The file view's sixth call is `pending_review`, which is `reviews` under
   another name. It is genuinely needed (the tray and the composer's button label
   both depend on it) and it is correctly uncached, so this is not waste — but it
   means the file view cannot get below 6 without a cheaper way to ask "does this
   viewer have a pending review".

Turbo prefetching is off globally (`<meta name="turbo-prefetch" content="false">`),
which is the single most valuable rate-limit decision in the app and is well
argued in the layout comment.

## Test gaps

Ranked by how likely each is to let a real GitHub response break the app
silently. The fixture inconsistency is filed above as **M3** because it is a
correctness problem, not only a coverage one.

1. **Nothing can catch H1.** Every `bodyHTML` in every fixture is benign
   (`review_threads.json:32,58,105,148,191`). A test that renders a comment whose
   `bodyHTML` contains `<img onerror>` and asserts the attribute is gone would
   have caught it, and would keep it caught.

2. **Multi-line anchors are never posted.** `ReviewCommentsController#build_anchor`'s
   multi-line branch (`:85-89`) has no integration or system coverage;
   `pull_request_files_test.rb:90-94` checks `data-anchor` only for
   `anchor["line"].is_a?(Integer)` and never asserts `start_line` / `start_side`.
   Coverage exists only in `anchor_test.rb` and `anchor_resolver_test.rb`, which
   never touch the wire.

3. **No LEFT-side comment is ever written end-to-end.** `side_sym`
   (`review_comments_controller.rb:94`) is only ever driven with `"RIGHT"`.
   Given that the one rule most likely to cause a mis-anchored comment is "a LEFT
   anchor carries a base line, never `right_of_left`", a test that posts one and
   asserts the exact payload is worth more than several unit tests.

4. **The pending-review 422 recovery is never triggered.**
   `review_comments_controller_test.rb:76-93` is named for the "review already
   exists (422)" path but stubs `/reviews` with `fixture: :reviews`, which already
   contains a PENDING review for `prism-dev` — so `ensure_pending_review` returns
   on its first line and `create_pending_review` is never called. The rescue at
   `comment_writer.rb:50-51` has zero coverage anywhere.

5. **`reviewThreads` pagination cannot detect dropping page two.**
   `client_test.rb:333-350` sets page two's `nodes` to `[]` and asserts
   `assert_equal 5, result.threads.size` — page one already has 5. Deleting the
   `threads.concat` for subsequent pages still passes. Give page two a node and
   assert 6.

6. **`reactionGroups: []` is not a shape GitHub returns.** GitHub sends a group
   for every `ReactionContent` with `reactors.totalCount: 0`.
   `build_reaction_groups` handles it correctly, but no fixture exercises the
   realistic payload, so a regression in the `count.zero?` filter would ship a row
   of empty pills and pass here.

7. **Renamed-with-content-change is untested.** `pull_files.json:38-49` is a
   *pure* rename with no patch, so `Review::Page#load_sources` never takes the
   `file.base_path` branch and `Page#paths` never filters a thread onto the old
   path. Per `docs/research/github-api.md` §2.4, a renamed file with changed
   content has both sides plus `previous_filename` — entirely uncovered.

8. **Threads on a removed strip never render.** `Page#removed_strip_threads`
   (`page.rb:106`) and its call site in `_removed_strip.html.erb:37` are dead in
   tests: `page_test.rb:240-257` passes `threads: []`, and the shared fixture
   produces no strip at all.

9. **Vacuous assertions worth tightening.**
   `client_test.rb:765` is named "422 mentioning the diff becomes
   LineNotCommentable" but asserts `assert_raises(Github::GraphQLError)` — the
   opposite of the name, and the gap the controller papers over with a regex at
   `review_comments_controller.rb:223` is itself untested.
   `review_threads_controller_test.rb:357` asserts `"Resolved"` appears, but the
   refetch is stubbed with a hardcoded `isResolved: true`, so it reads the stub
   rather than the mutation; the `unresolve` test makes no DOM assertion at all.
   `mentionables_controller_test.rb:339-341` asserts only that the response is an
   array of hashes with a `login` key — it would pass if the controller returned
   the wrong repository's people.

10. **Brittle system-test selectors.** `file_view_test.rb:156-158` reads
    `opacity` with `assert_equal` immediately after `.hover`, racing a 150 ms
    Tailwind transition on `.md-add` — `assert_equal` does not retry.
    `file_view_test.rb:253-258` uses a fixed `sleep 0.5` before a negative
    request assertion; the same behaviour is already pinned deterministically in
    `repos_test.rb:292`.

11. **Untested error branches on the write path.** `ReviewsController`'s unknown-

## Things done well

- **`Markdown::Sanitizer` earns its "security boundary" comment.** Sixteen
  payloads, including three `javascript:` encodings, `data:` URLs on both `href`
  and `src`, `formaction`, SVG `<animate onbegin>`, and the `<math><mtext>` and
  `<noscript>` mXSS classics — all neutralised. The decision to sanitize *after*
  Rouge and to add wrapper markup *after* sanitizing, through Nokogiri's DOM API
  rather than by re-parsing strings, is the right ordering and is documented at
  both ends.

- **`Diff::Patch` handles the three details that actually bite.** Optional hunk
  counts, `\ No newline at end of file` consuming no line, and an empty-string
  context line counting as context. Each is called out in the comment with the
  consequence of getting it wrong.

- **`Review::Anchor`'s invariants are enforced in the constructor**, including the
  undocumented `start_line < line` rule, and the class refuses to serialise a
  file-level comment into a review's `comments` array rather than emitting
  something GitHub will reject. `to_rest` / `to_review_comment` / `to_graphql`
  being three separate methods, with the reason written down, is exactly right.

- **Cache namespacing is airtight.** `Github::Client#cached` prefixes every key
  with `user.id`, and there is no other `Rails.cache` call in the application.

- **Route parameters are escaped before they reach an API path.**
  `escape` is `ERB::Util.url_encode`, and `contents_path` escapes per segment so
  slashes survive without letting `..` traverse. Verified that Octokit's
  `Addressable::URI#normalize` does not undo it.

- **`Review::Page` degrades rather than failing.** Rendering the document with a
  banner when threads are unavailable, and distinguishing a rate limit (ends at a
  known time) from anything else (just missing), is a judgement most apps get
  wrong in the other direction.

- **The comments explain decisions, not mechanics.** `Github::GraphQL`'s two
  traps, `Markdown::Renderer`'s note on why `to_html` on a `table_row` panics the
  Rust extension, and the layout's argument for disabling Turbo prefetch are all
  things the next person would otherwise have to rediscover the hard way.
